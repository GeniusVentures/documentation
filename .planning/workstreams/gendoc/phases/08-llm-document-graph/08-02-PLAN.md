<objective>
Extend the Ask AI worker's TypeScript types, catalog loader, and scoring function to consume graph metadata from the enriched llms-meta.json produced by build-graph.py. This implements the worker-side integration of the LLM document graph (D-06), adding optional graph fields to CatalogEntry, fetching and merging llms-meta.json graph data during catalog loading, and enhancing scoreEntries with questions_answered matching, authority scoring, graph-based ranking, and redundancy deduplication — without replacing lexical retrieval (LLMGRAPH-05).

Purpose: The worker currently ranks documents using only title/description/URL term matching. With graph metadata, queries that match questions_answered fields get better results, high-authority documents get priority, graph relations boost connected documents, near-duplicate results are pruned, and the composite relevance scoring formula R(d,q) from LLMGRAPH-05 is fully approximated in the worker's scoring function.

Output: Extended types.ts with GraphMetadata interfaces and MetadataOrigin union, enhanced catalog.ts with llms-meta.json fetching and graph-enriched scoring, utils.ts with configurable weight constants.
</objective>

    ```typescript
    export const kQuestionMatchWeight = 4;   // questions_answered term match bonus
    export const kTopicMatchWeight = 2;       // topics term match bonus
    export const kAuthorityThreshold = 0.7;   // minimum authority_score for +1 bonus
    export const kHighAuthorityThreshold = 0.9; // minimum authority_score for +2 bonus

    ```

    **Step B — Enhance scoreEntries function in catalog.ts:**

    Modify scoreEntries function (currently lines 54-88) to incorporate graph metadata into scoring. This implements the LLMGRAPH-05 composite scoring approach — LLM metadata improves M (metadata-question match), G (graph support), and A (authority/freshness) components with configurable weights, plus D (redundancy penalty).

    After the existing term-based scoring loop (lines 61-66), add graph-based scoring that runs when e.graph is present:

    1. **questions_answered term matching** (M component — metadata-question match):
       - If e.graph.questions_answered exists, for each answered question, check if any search term appears in the question text (case-insensitive)
       - For each match, add `kQuestionMatchWeight` to score (higher weight than title match per LLMGRAPH-07 priority)
       - Also check term match against e.graph.topics[].value — add `kTopicMatchWeight` per topic match

    2. **authority bonus** (A component — authority and freshness):
       - If e.graph.authority_score is defined and >= `kAuthorityThreshold`, add `kAuthorityBonus` to score
       - If e.graph.authority_score is defined and >= `kHighAuthorityThreshold`, use `kHighAuthorityBonus` total (not additive on top of kAuthorityBonus)
       - Apply only when entry already has a positive base score from lexical matching

    3. **Freshness bonus** (A component):
       - If e.graph.freshness_score is defined and >= `kFreshnessThreshold`, add `kFreshnessBonus` to score
       - Apply only when entry already has a positive base score

    4. **Graph support G(d,q)** (Issue 3b):
       - After all entries have been scored (post-loop), build a scored-entry lookup map keyed by title/URL
       - For each entry with e.graph.relations, find relations of type 'depends_on' where the target document also appears in the catalog and has a positive score
       - Add bonus to the source document: `bonus = Math.round(targetEntry.score * relation.weight * kGraphRelationBonus / 10)`
       - This implements G(d,q): documents that depend on highly-ranked documents get a proportional boost. The factor includes relation.weight (from the LLM's confidence) and the target's score.

    5. **Redundancy penalty D(d,S)** (Issue 3c):
       - After scoring and the graph bonus pass, sort entries by score descending
       - Walk the sorted list building a `selected` set
       - For each entry, compute a title similarity check against already-selected entries: normalize titles (lowercase, strip punctuation, tokenize) and compute Jaccard similarity of word sets
       - If similarity >= `kDedupSimilarityThreshold` with any already-selected entry, remove (or push to end with zero score) — the higher-scored document stays
       - This implements D(d,S): prevents near-duplicate documents from crowding the top results

    **Document role weighting for conflict resolution** (LLMGRAPH-06):
    - Add a rolePriority constant map at the top of the function: normative_standard: 5, architecture_specification: 5, implementation_reference: 3, tutorial: 1, FAQ: 1 (highest priority roles from the SPEC conflict resolution)
    - Apply role priority as a tiebreaker: when two entries have equal scores, the one with higher role priority ranks first
    - This can be done by adding rolePriority to the tiebreak calculation in the sort comparator

    All graph scoring must be gated on the entry already having a positive base score from lexical matching (e.score > 0). The gate prevents every entry with graph data from getting a baseline score — graph data enhances, not replaces, lexical retrieval.

    Do NOT remove or weaken existing term-based scoring (title +3, desc +2, url +1). Graph scoring is additive, not substitutional. The composite formula R(d,q) from LLMGRAPH-05 is fully approximated here within the worker's scoring function: lexical matching provides the base, M (questions_answered/topics) boosts relevance, A (authority/freshness) prioritizes trustworthy docs, G (graph support) boosts connected docs, and D (redundancy penalty) prunes near-duplicates.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| llms-meta.json (CDN) to Worker fetch | Worker fetches llms-meta.json from origin — data is from build pipeline, not user input |
| Graph metadata to scoring function | Graph data from llms-meta.json flows into scoreEntries — must handle absent/corrupt data |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-09 | Tampering | llms-meta.json fetched by worker | mitigate | Worker uses HTTPS fetch; JSON parse failures return gracefully (no crash); graph field is optional — absence of graph never breaks scoring |
| T-08-10 | Denial of Service | Large llms-meta.json fetch | mitigate | Metadata file is produced at build time and typically small (under 500 KB for corpus); fetch uses Cloudflare cache (cf cacheTtl as in existing fetchText pattern); cache lifetime matches CATALOG_TTL_MS |
| T-08-11 | Elevation of Privilege | Injected graph data in scoring | accept | Graph metadata is additive only — it increases scores but never grants access or elevates privileges; worst case is a lower-quality search result; data source is the build pipeline (trusted) |
| T-08-12 | Information Disclosure | Graph metadata exposed in responses | accept | Graph metadata only flows into scoring — it is never included in SSE messages or model context; questions_answered and topics are internal ranking signals, not sent to users or LLMs |
</threat_model>
